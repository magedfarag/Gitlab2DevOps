# 04. Value Streams

## Purpose

A value stream describes how an idea becomes value for a customer, from request to cash or impact. It cuts across teams, tools, and functions.

We use value streams to see flow, find bottlenecks, and decide where DevSecOps investments give the best return.

## Why Value Streams Matter

Local optimisation does not guarantee faster delivery end to end. Many delays occur outside coding:

- Slow approvals.
- Manual handovers between teams.
- Inconsistent environments.
- Long waits for testing or deployment windows.

Value stream mapping makes these delays visible. It provides a shared picture for product, engineering, operations, and security.

## Anatomy of a Software Value Stream

Typical stages:

1. Idea and demand.
2. Discovery and refinement.
3. Design and planning.
4. Implementation.
5. Verification.
6. Release and deployment.
7. Operation and learning.

When you map a value stream, mark for each stage:

- Lead time.
- Waiting time versus active work.
- Rework loops and failure points.
- Handoffs between roles or teams.

## Metrics for Value Streams

Key metrics:

- Lead time for changes.
- Deployment frequency.
- Change failure rate.
- Time to restore service.

These match DORA metrics and give a consistent language across teams.

You can also track:

- Work in progress.
- Number of handoffs.
- Percentage of time spent on unplanned work.

## Using Value Streams to Improve

1. Map the current state with people from product, engineering, QA, operations, and security.
2. Identify constraints, queues, and rework.
3. Design a target state that removes unnecessary approvals and moves checks earlier.
4. Run small experiments and measure impact on lead time and failure rate.
5. Revisit the map after big organisational or technical changes.
