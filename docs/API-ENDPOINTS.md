# API Endpoints Reference

This document lists the Azure DevOps and GitLab REST API endpoints used by this repository, why they are used, an official reference link, and a short assessment whether the endpoint is the best choice for the task.

Notes:
- Most Azure DevOps calls are relative to the configured collection URL and require the `api-version` query parameter (the modules often pass `api-version` or rely on the client to provide a default).
- GitLab endpoints are typically under `/api/v4/` (this project uses GitLab API v4 patterns).

## Notes and Recommendations

- The repository correctly favors official REST endpoints for Azure DevOps and GitLab. Those are generally the best options for idempotent, server-side operations.
- For extremely large binary transfers or full-git mirror pushes, prefer using native `git` commands (mirror push, `git push --mirror`) rather than REST push endpoints — they are faster and more reliable for large repositories. The codebase already uses pushes via REST for some operations and local `git` for others; consider using git remotes for heavy workloads.
- Ensure `api-version` is set consistently. The codebase sometimes passes `api-version=7.1` explicitly for testplan/test-related calls; keep these up-to-date with supported API versions for the target server.
- Security endpoints (`securitynamespaces/.../accesscontrolentries`) are powerful but low-level; when possible prefer high-level team/group membership APIs to avoid mis-scoped ACL changes.
